# 共同編集：インターネット越しの中継

LAN / VPN の外にいる共著者とも共同編集できるようにする。今の作り（ホストの Mac が原本を持ち、Yjs の更新を
ゲストと交換する）はそのままにして、ホストとゲストをつなぐ経路だけを足す。

## 方針

- ホストもゲストも、Fermion が置く中継サーバー（Cloudflare Workers + Durable Objects）に外向きにつなぐ。
  中継は部屋（セッション）ごとに 1 つの Durable Object で、ホストとゲストの間でバイト列を流すだけ。
- 中継に任せるのは「動いていること」だけで、中身は任せない。中継（や、中継と組んだリンクの持ち主）が
  できるのは止めることだけで、読むこと・書き換えること・編集の権限を得ること・ホストやゲストに
  なりすますことはできない。中継が見るのは部屋の ID、接続の出入り、メッセージの長さだけ。
- ゲストの接続ごとに、ホストとの間に専用の暗号の通り道（チャネル）を作る（形は Noise NK）。
  招待リンクにはホストの X25519 公開鍵だけが入り、秘密鍵はホストの TeX64 の中にしかない。
- 認証は LAN と同じ。ゲストがチャネルの最初に送る hello の中の編集用 / 閲覧用トークンをホストが確かめ、
  閲覧のみの制限もホストが掛ける。hello はそのチャネルの鍵でしか開かないので、閲覧リンクを持つ人が
  中継と組んでも、編集する人のトークンは読めない。
- ホストの座は「ホストの秘密」（招待リンクには入れない）で守る。部屋の ID は秘密の SHA-256 の先頭 128 bit
  で、中継はホストがつないだときに秘密からその ID を計算し直して確かめる。
- 中継を使うのは、ホストの TeX64 に中継の URL が設定されているとき（`TEX64_COLLAB_RELAY_URL`）。
  未設定なら今までどおり LAN の経路を使う。ゲストは招待リンクの形で経路を選ぶので、設定は要らない。

## 招待リンク

```
tex64://collab/join?s=<中継の URL>&r=<部屋 ID>&k=<ホストの公開鍵>&t=<トークン>&n=<名前>
```

`s` は `wss://relay.example` のような ws(s) の起点（パスなし）。`r` は 128 bit、`k` は X25519 の公開鍵
（32 バイト）で、どちらも base64url。編集用と閲覧用のリンクは `t` だけが違う。LAN のリンク（`h` / `p`）は
そのまま使える。中継につなぐ URL は `<s>/rooms/<r>?role=host&secret=…`（ホスト）または `?role=guest`。

## チャネル

1. 中継がゲストに HOST_OPEN を送ると、ゲストは使い捨ての鍵 eₘ を作り、その公開鍵を送る。
2. ホストも使い捨ての鍵 eₕ を作り、その公開鍵を返す。
3. 双方が DH(eₘ, eₕ) と DH(eₘ, S)（S はホストの固定の鍵）から、HKDF-SHA256 でこのチャネルの 2 本の鍵
   （ゲスト→ホスト、ホスト→ゲスト）を作る。両方の公開鍵と S も鍵の材料に入れる。
4. ゲストは hello を送る。ホストからの最初のメッセージ（welcome）が開けたとき、ゲストは相手が
   S の持ち主だと分かり、「つながった」とする。

接続のたびに双方が新しい使い捨ての鍵を使うので、前の接続で記録したものを流し直しても開かない。

## チャネルの中身

| 種類 | 中身 |
| --- | --- |
| `0x01` | ゲストの使い捨て公開鍵（32 バイト） |
| `0x02` | ホストの使い捨て公開鍵（32 バイト） |
| `0x03` | 断片：列 u8・何番目 u16・全部で何個 u16・暗号文（AES-256-GCM、タグ 16 バイト） |
| `0x04` | 受け取り確認：列ごとにこれまで受け取った平文のバイト数（急ぎ u64・大きな荷物 u64） |
| `0x05` | 生存確認 |

- 1 つのフレーム（Yjs の更新、図版など）は 256 KiB ごとの断片にし、断片ごとに封をする。nonce は向きごとの
  通し番号で、断片の見出し 6 バイトを追加認証データにする。流し直し・抜け・順番の入れ替え・偽造は開かずに
  失敗し、その接続を閉じる。ゲストはつなぎ直し、状態ベクトルから同期し直す。
- チャネルには列が 2 本ある。図版（blob のフレーム）は「大きな荷物」、それ以外（編集・カーソル・制御）は
  「急ぎ」で、急ぎを先に送る。ただし大きな荷物にも 1 秒に 1 回は番を回すので、編集が続いても途中の図版は
  止まらない（止まると受け取り側が 60 秒で接続を切るため）。列ごとに 1 つずつフレームを組み立てるので、
  図版の途中でも編集が届く。
- 送る側は、相手がまだ受け取り確認をしていない分を、急ぎは 4 MiB、大きな荷物は 1 MiB までに抑える。中継の
  中で編集の前に溜まる図版は 1 人あたり 1 MiB まで。1 人分の送り待ちが 512 MiB を超えたら、その接続を閉じる。
- 受け取り確認は 256 KiB 受け取るごとにまとめて送り、ソケットが詰まっているあいだは待つ。小さなフレームを
  大量に送られても、確認の書き込みは溜まらない（送る側は各列の上限で止まるので、その前に必ず確認が届く）。
  生存確認も、ソケットが詰まっているあいだは送らない。
- ソケットの送り待ちは 1 MiB まで（家庭の上り 1 MB/s でも 1 秒ほど）。ホストは 1 本のソケットを全員で使うので、
  ゲストの間で 1 断片ずつ順番に送る。
- 同じゲストに同じ図版を送るとき、送り待ち（送信中を含む）の中でその図版の最後に積まれたものが同じ版
  （同じハッシュ）なら、重ねて積まない。A→B→A のように前の版に戻したときは最後の A も積むので、最後の版が
  必ず最後に届く。同じ図版を何人かに送るときは、1 つのフレームを共有する。ゲストは届いていない図版を、30 秒に 1 回までしか頼み直さない
  （つなぎ直したときは頼み直す）。
- ホストが組み立て途中で抱えるのは全員で 256 MiB まで。hello より前は 64 KiB、閲覧のみの人からは 1 MiB
  より大きいフレームを受け付けない。60 秒新しい断片が来ない組み立て途中のフレームは、その接続ごと捨てる。
- 双方とも 25 秒ごとに中継へ "ping" を送り（中継は Durable Object を起こさずに "pong" を返す）、チャネルにも
  生存確認を送る。中継から 60 秒、チャネルの相手から 75 秒何も来なければ、黙って切れたとみなしてつなぎ直す。

## 中継とのやり取り

ホスト ↔ 中継：1 バイトの種類 + 接続 ID（u16 長 + UTF-8）+ 中身。

| 種類 | 向き | 意味 |
| --- | --- | --- |
| `0x01` SEND | ホスト → 中継 | その接続のゲストへ送る |
| `0x03` CLOSE_PEER | ホスト → 中継 | その接続を閉じる（中身は u16 の閉じる理由コード） |
| `0x11` PEER_OPEN | 中継 → ホスト | ゲストがつないだ（ホストが来たときは待っていたゲスト全員分） |
| `0x12` PEER_DATA | 中継 → ホスト | ゲストからの中身 |
| `0x13` PEER_CLOSE | 中継 → ホスト | ゲストが切れた |
| `0x14` REFUSED_HOST | 中継 → ホスト | 中継がホストを断る（中身は u16 の理由コード） |
| `0x15` HOST_READY | 中継 → ホスト | ホストの座を渡した（ホストはこれを受けてからセッション開始とする） |

ゲスト ↔ 中継：ゲストが送るものはチャネルの中身そのまま。中継からゲストへは 1 バイトの種類 + 中身。

| 種類 | 意味 |
| --- | --- |
| `0x21` HOST_DATA | ホストからの中身 |
| `0x22` HOST_OPEN | ホストが部屋にいる（ゲストは新しいチャネルを作る） |
| `0x23` HOST_GONE | ホストが部屋を離れた |
| `0x24` REFUSED | 中継がゲストを断る（中身は u16 の理由コード） |

中継が接続を閉じるときは、先に REFUSED / REFUSED_HOST で理由コードを送り、受け取った側が自分で閉じる
（workerd では中継側から閉じると、閉じ終わるまで 10 秒以上かかることがあるため）。

閉じる理由コード：4004（リンク違い。鍵が違って hello が開けないときも）、4005（満員）、1000（ホストが
セッションを終えた）はゲストが諦める。4010（部屋にホストがいない）は 15 秒おきに、それ以外は間隔を
空けてつなぎ直す。4001 は hello の期限切れ、4003 は壊れた・開けないメッセージ、4008 は送り待ちや
組み立て途中の上限超え、4009 は別のホストに座を取られた、4012 は相手が黙ったとき、4013 は部屋の予約を
確かめられなかったとき（間隔を空けてつなぎ直す）、4029 はその接続元が持てる部屋の数を超えたとき（開始時
なら「このネットワークから開いているセッションが多すぎます」と出し、つなぎ直しなら 1 分おきに試す）。

## 中継の守り

- 部屋を作るのはホストだけ。ホストが一度も来ていない部屋には、ゲストは入れない（4010）。ホストが離れた
  部屋では、ゲストは 2 分まで待てる。それを過ぎるとアラームでゲストを帰す。
- Durable Object は WebSocket の Hibernation API を使う。何も流れていない部屋は眠り、費用がかからない。
  起きたときは、各ソケットに付けた印（役割と接続 ID）と、保存した「ホストが離れた時刻」から部屋を組み直す。
  接続が閉じたことで起きたときは、そのソケットはもう閉じていて組み直しに入らないので、印から退出を
  処理する（ホストなら猶予の開始とゲストへの通知、ゲストならホストへの通知）。別のホストに置き換わった
  あとの古いホストの退出では、座は終わらない。
- 1 つの接続元のアドレスがホストとして同時に持てる部屋は 20 まで。アドレスごとの Durable Object が予約を
  持ち（`room.mjs` の `updateQuota`）、規則は次のとおり。
  - ホストの接続ごとに「座の番号」があり、予約にはその番号が付く。予約を返せるのは同じ番号の接続だけ
    なので、つなぎ直したホストと古い接続の終了が重なっても、新しいホストの予約は消えない。
  - 1 つの部屋では、ホストの入室（予約→着席→置き換えた座の返却）、予約の延長、ホストの退出（返却）を
    必ず 1 つずつ順番に行う。予約の問い合わせを待つあいだに他の処理が割り込んでも、予約は着席と退出の
    順番どおりになる。
  - 予約の期限は 24 時間。ホストが座っているあいだは、部屋のアラームが 6 時間ごとに今のホストの番号で
    予約を取り直して延ばす。答えが失われて終わらなかった入室が別の番号を残していても、ここで取り戻す。
    延ばせなかったときは、その座を 4029 で終える。予約の Durable Object が答えなかったときは座を保った
    まま 5 分後に試し直し、座るときに答えなかったときは 4013 で断る（ホストは間隔を空けてつなぎ直す）。
    閉じる知らせが失われた分は、延ばす者がいないので 24 時間で消える。
  - ホストが置き換わったとき（つなぎ直し。別のネットワークからでも）は、古い座の予約をその場で返す。
- 1 部屋のゲストは 10 人まで（LAN と同じ）。中継を通る 1 メッセージは 1 MiB まで。
- 接続の試みは送り元のアドレスごとに 1 分 120 回まで（Workers の Rate Limiting）。

## ファイル

- `services/collab-relay/room.mjs`：部屋の処理。Worker と手元の中継で共有する。
- `services/collab-relay/worker.mjs` と `wrangler.toml`：Cloudflare に置く Worker と Durable Object。
- `services/collab-relay/local-server.cjs`：手元の中継（`node services/collab-relay/local-server.cjs 8787`）。
  テストと、デプロイ前に中継の経路を試すのに使う。テストでは中継が攻撃する側も演じる。
- `electron/services/collab/relay-transport.cjs`：TeX64 側の経路（チャネル、`RelayHostTransport` /
  `RelayGuestTransport`）。`HostTransport` / `GuestTransport` と同じ口なので、ハブは経路を区別しない。
- `tests/collab-relay.test.cjs`：受け取り確認の範囲、流し直し・順番違い・偽造、部屋の入室規則、
  2 つのハブの同期・閲覧のみ・中継が平文を見ないこと・3 MiB の図版・ホストの再接続、中継による図版の
  流し直し・hello の差し替え・ホストへのなりすまし、黙って切れた接続、鍵違いのリンク、ホストのいない部屋、
  中継に届かないとき、受け取り確認のまとめ方、休止から起きたときの退出、アドレスごとの部屋の数、
  予約の延長と座の番号、置き換わったホストと別アドレスへの移動。

## 試験（Cloudflare、2026-11-04）

個人アカウントに `tex64-collab-relay.p-c-aces1056.workers.dev` として置き、ホストとゲストを別々のプロセスで
動かした（同じ Mac。上り 0.9〜1.1 MB/s、下り 1.8 MB/s）。

| 試験 | 結果 |
| --- | --- |
| 10 人に 5 MiB の図版 | 10 人とも 19〜21 秒で受け取る。ホストのメモリ最大 141 MiB、送り待ち最大 1 MiB |
| 参加時に 50 MiB を 2 人、1 人は 20 秒受信を止める | 32 秒と 51 秒で受け取る。止めた人がもう 1 人を待たせない |
| 参加後に 50 MiB を 2 人へ | 53 秒で受け取る。その間の編集の遅れは中央値 0.7 秒・最大 1.1 秒 |
| 閲覧者が小さなメッセージを 10 万回 | 送り待ち 0、メモリ最大 98 MiB、編集の遅れ中央値 0.17 秒、誰も切れない |
| 入室の規則・秘密違い・ping・部屋の数・休止中の退出 | 手元の workerd と同じく通る |

試験の途中で 2 つ直した。ソケットの送り待ちが 16 MiB だったときは、上り 1 MB/s では ping や welcome が
16 秒以上待たされ、ホストとゲストが切れてはつなぎ直すのを繰り返した（列の分割・送り待ちの縮小・順番に
送るで直した）。また、届いていない図版をゲストが 3 秒ごとに頼み直し、ホストが同じ 50 MB を何度も積んで
送り待ちの上限（4008）に達していた（重ねて積まない・頼み直しを 30 秒に 1 回にするで直した）。

## 残り

- 会社の Cloudflare アカウントと独自ドメインに置き直し、製品版の既定の経路を中継に切り替える（LAN は設定で残す）。
- 参加は図版をすべて受け取るまで終わらない（LAN と同じ作り）。インターネット越しでは大きな図版のある
  プロジェクトの参加に時間がかかるので、本文がそろった時点で開き、図版はあとから受け取る形を検討する。
